## 02-2. 作業を決めて試し撮り 
例：ブロックをA地点からB地点へ移す。1回記録し、映像・関節位置・操作指令を確認する。

### A. 作業内容
　・黒いリーダーで白いフォロワーを操作し、黄緑のワークをつかみ、持ち上げて赤い入れ物へ移し、爪を開いて置く。 <br>

### B. 動作確認・調整
　- 記録前にリーダーとフォロワーの姿勢を近づけ、追従を確認した。 <br>
　- 肩・肘の上方向への追従が止まる症状に対し、現在位置から目標位置までの差の制限を調整した。 <br>
　- 肩の上下・肘は4度、その他の関節は設定値3で試行し、ワークを入れ物へ置くまでの動作を確認した。 <br>
　- 制御・記録の設定は30fpsとした。 <br>
　- 終了時の脱力による落下を防ぐため、プログラム終了後もフォロワーの保持トルクを残す設定を使用した。<br>
 　　電源を切る際は、アームを支えてから切る。 <br>

### C. 試し撮りの結果
　・試行 `retry04` で、黄色いワークを赤い入れ物へ置く作業に成功した。記録処理と動画のエンコードはエラーなく終了した。 <br>

## 02-3. 実演データを集める 
同じ作業を繰り返して記録し、成功した実演データを学習用にまとめる。

SO-101のリーダーを操作し、フォロワーによる「黄緑のワークをつかみ、持ち上げ、赤い入れ物へ運んで置く」実演を収集した。<br>
成功実演20件を採用し、模倣学習用データセットを作成した。<br>

#### 収集方法

- 白いフォロワーと黒いリーダーを使用し、保存済みのキャリブレーションを再利用した。
- 作業領域をロボットの向かい側から1台のカメラで撮影した。
- 試し撮りで画角を調整した後、同じ画角・制御設定で収集した。
- 集中力を維持しやすいよう、5件ずつ4回に分けて収集した。
- 各回は操作者のEnter入力を開始の合図とし、保存完了後に成功・失敗を記録した。次の実演前に黄緑のワークとアームを戻した。
- 通算8件目は撮り直し、元の8件目を除いて撮り直した実演を採用した。

| 項目 | 内容 |
|---|---|
| 採用実演数 | [20エピソード](datasets/video/) |
| カメラ画像 | 640 × 480、RGB |
| 記録の設定fps | 30 |
| 数値データ | `observation.state`、`action`、それぞれ6要素 |
| 対象関節 | 土台回転、肩、肘、手首曲げ、手首回転、グリッパー |
| データ形式 | LeRobot Dataset v3.0 |

#### データ検査と統合

5件ごとに数値データと動画を検査し、撮り直した8件目も同様に確認した。

- メタデータと数値データの行数が一致すること。
- `observation.state`と`action`が6要素で、NaN・無限大がないこと。
- フレーム番号が0から連続し、時刻が単調増加して設定fpsと一致すること。
- 動画を全フレーム読み取れ、解像度が640 × 480であること。
- 動画と数値データのフレーム数が一致すること。

終了後の待機区間を実演ごとに整理し、元データを変更せずに別の学習用データセットへ統合した。<br>
採用元データは合計20,650フレーム、整理・統合後は20エピソード、15,540フレームとなった。

統合後も、数値データが保持されていることと、動画のフレーム数が一致することを確認した。<br>
動画はH.264で再エンコードしたため、元動画とのバイト単位の一致を意味するものではない。

今回の検査はファイル構造・数値・時刻の整合性を確認するものであり、全画像が異なることや、カメラと関節データの実時間での同期精度まで保証するものではない。

**結果：成功実演20件を採用し、学習用データセットの準備を完了した。**

### 3-1 学習環境の確認

Windows上のWSL2／Ubuntu環境で、LeRobotとPyTorchによるGPU学習が実行できることを確認した。

| 実行環境 | WSL2／Ubuntu、Python仮想環境 `lerobot` |
| Python | 3.12.3 |
| LeRobot | 0.6.1 |
| PyTorch | 2.11.0+cu130 |
| GPU | NVIDIA ***** 、VRAM ** GiB |
| PyTorchのCUDA利用 | `True` |
| Accelerate | 1.15.0（不足していた依存関係を追加） |
| 依存関係検査 | `No broken requirements found.` |

CUDAを使った小規模な行列計算、ACT本体の読み込み、学習処理の動作確認を行った。学習には保存済みデータを用い、ロボットやカメラへの接続は必要としない。

#### 環境構築時に対応した点

- `accelerate`が未導入で学習開始に失敗したため、依存関係を追加して再確認した。
- データセット作成時、`RGBEncoderConfig`に指定した`libx264`はこの環境では受け付けられなかった。設定値を`h264`に変更して作成を完了した。
- 使用中のLeRobotのソースと設定を確認し、インストール済みバージョンに合わせてスクリプトを作成した。

**結果：GPUでACTの学習を実行できる環境を確認した。**

### 3-2 模倣学習と評価

収集した実演20件を使ってACT（Action Chunking with Transformers）を学習した。学習済みモデルを実機で評価し、黄緑のワークをつかんで赤い入れ物へ置くタスクの初回成功を確認した。

#### 学習設定

ACTはカメラ画像と関節状態を入力し、複数ステップ分の動作をまとめて予測するモデルである。今回は以下の設定で学習した。

| 項目 | 設定 |
|---|---|
| データセット | `local/so101_yellow_pick_place_20_trimmed_v1` |
| 分割 | 学習16エピソード、評価4エピソード |
| 学習データのフレーム数 | 12,720 |
| 入力 | 作業領域のRGB画像1枚＋6要素の関節状態 |
| 出力 | 6要素のaction |
| 画像バックボーン | ResNet-18、ImageNet事前学習重み |
| 学習ステップ数 | 10,000 |
| バッチサイズ | 2 |
| 学習率 | `1e-5` |
| 数値精度 | FP32（`use_amp=false`） |
| `chunk_size` / `n_action_steps` | 100 / 100 |
| Temporal ensemble | 使用しない |
| 評価間隔 | 2,000ステップ |
| 保存間隔 | 5,000ステップ |
| seed | 42 |

学習は約36分29秒で終了し、終了コードは0だった。

#### オフライン評価

| ステップ | eval_loss |
|---:|---:|
| 2,000 | 0.4850 |
| 4,000 | 0.4688 |
| 6,000 | 0.3989 |
| 8,000 | **0.3944** |
| 10,000 | 0.4118 |

評価損失の最小値は8,000ステップ時点だった。ただし、今回の保存設定では5,000ステップと10,000ステップのモデルのみ保存しており、8,000ステップのモデルは残っていない。実機評価には10,000ステップのモデルを使用した。

```text
act_16train_4eval_fp32_20261113_161537/checkpoints/010000/pretrained_model
```

次回は評価のタイミングに合わせたチェックポイント保存、または評価損失が最小となったモデルを保存する処理を用意する。評価損失と実機での作業成功率は別の指標として扱う。

#### 実機評価の経過

短時間の動作確認から開始し、接近方向、把持、運搬、投入を確認した。途中では、把持位置のずれ、開始位置付近で動かない、把持できても制限時間内に運搬まで進まない、といった結果があった。

`n_action_steps`を短くする試行も行ったが、今回の試行では開始位置付近で進まなくなったため、最終的には100に戻した。照明と開始姿勢も試行間で変化しており、失敗の原因をいずれか1つに断定できる比較にはなっていない。

開始姿勢を調整し直した後、45秒の試行では把持に失敗して赤い入れ物へ移動し、その後ワークへ再接近したところで時間切れとなった。次の試行ではプログラムの制限時間を60秒に変更し、タスクの成功を確認した。再接近した動きだけから、モデルが把持失敗を認識したとは判断していない。

チャットに記録された、実際にロボットが動いたACT評価を数えると、**10回目で初めてタスクを完遂した**。この回数には短時間の確認試行を含み、接続エラーで動かなかった回や姿勢合わせ・肘の単独試験は含めない。最後の姿勢調整後では2回目の評価だった。

試行時間や開始条件を変更しながら進めた開発中の評価であるため、この記録を「同一条件で10回評価した成功率10%」とは扱わない。

全コピーのSHA-256一致を確認し、Ubuntu側の元データも保持した。保存済み動画のGitHub掲載は別途行う。

#### 今回わかったことと次の課題

- **初回成功を確認した。** 同じ条件で繰り返し評価した再現性・成功率の測定は未実施。
- 次回は開始関節値、ワーク位置、カメラ画角、照明を記録してそろえ、変更項目を1つずつにする。
- 関節角度を目標値へ合わせるだけでは、途中の経路が机に接触する可能性がある。今回の自動姿勢合わせでも接触が発生したため、経路を確認せずにそのまま再利用しない。
- キャリブレーションの不一致が繰り返された。保存値の復元と読み戻し一致は確認したが、電源再投入後の保持については継続確認が必要。
- 日中の収集と夜間の評価で照明条件が異なった。照明の影響は単独では切り分けられていない。
- 評価損失が最小のモデルを保存し、最終ステップのモデルと比較できるようにする。
